## **KMS (Key Management Service)** - Служба управления ключами

## **Основное определение**

**KMS** — это облачный сервис (или локальное решение), предназначенный для **создания, хранения, управления и контроля доступа** к криптографическим ключам.

## **Аналогия для понимания**

Представьте себе банк:
- **KMS** — это банковская ячейка с усиленной охраной
- **Ключи** — это ценности в ячейке
- **Политики доступа** — это процедуры доступа к ячейке
- **Аудит** — это журнал посещений банка

## **Основные функции KMS**

### **1. Управление жизненным циклом ключей:**
```
Создание → Активация → Использование → Деактивация → Удаление
```
- **Генерация ключей** (RSA, EC, AES, симметричные/асимметричные)
- **Импорт собственных ключей** (BYOK - Bring Your Own Key)
- **Ротация ключей** (автоматическая и ручная)
- **Архивация и удаление** с retention политиками

### **2. Безопасное хранение:**
- **Ключи никогда не покидают** KMS в открытом виде
- **HSM под капотом** (аппаратные модули безопасности)
- **Геораспределенное хранение** (multi-region)
- **Резервное копирование** и репликация

### **3. Выполнение операций:**
- **Шифрование/дешифрование** (без экспорта ключа)
- **Подпись/верификация** данных
- **Генерация HMAC**
- **Обертка/развертка ключей** (key wrapping)

### **4. Управление доступом:**
- **Fine-grained IAM политики** (кто, что, когда)
- **Разделение обязанностей** (Dual Control)
- **Временные доступы** (time-based policies)
- **Условный доступ** (context-aware)

## **Ключевые концепции**

### **1. Customer Master Key (CMK) / Key Encryption Key (KEK):**
- **Ключ верхнего уровня**, шифрует другие ключи
- **Никогда не покидает** HSM
- **Используется для** envelope encryption

### **2. Data Encryption Key (DEK):**
- **Ключ для шифрования данных**
- **Генерируется приложением**, шифруется CMK
- **Хранится рядом с данными** (в зашифрованном виде)

### **3. Envelope Encryption (Конвертное шифрование):**
```
┌─────────────────────────────────────────┐
│           Ваши данные                   │
├─────────────────────────────────────────┤
│   Зашифрованы с помощью DEK             │
├─────────────────────────────────────────┤
│   DEK зашифрован с помощью CMK          │ ← Хранится рядом с данными
├─────────────────────────────────────────┤
│   CMK защищен в KMS/HSM                 │ ← Никогда не покидает KMS
└─────────────────────────────────────────┘
```

### **4. BYOK (Bring Your Own Key) / HYOK (Hold Your Own Key):**
- **Импорт собственных ключей** в KMS
- **Контроль над ключевым материалом**
- **Требования соответствия** (регуляторы, стандарты)

## **Примеры использования**

### **Пример 1: Шифрование базы данных**
```python
# Псевдокод использования AWS KMS
import boto3

kms = boto3.client('kms')

# 1. Генерация DEK
response = kms.generate_data_key(
    KeyId='alias/my-database-key',
    KeySpec='AES_256'
)

# DEK в открытом виде только в памяти
plaintext_dek = response['Plaintext']
encrypted_dek = response['CiphertextBlob']  # Для хранения

# 2. Шифрование данных
from cryptography.fernet import Fernet
cipher = Fernet(plaintext_dek)
encrypted_data = cipher.encrypt(b"Secret database data")

# 3. Храним: encrypted_data + encrypted_dek
# 4. При чтении - расшифровываем DEK через KMS, потом данные
```

### **Пример 2: Auto-unseal для Hashicorp Vault (как в вашем случае)**
```hcl
# Vault config.hcl
seal "awskms" {
  region = "eu-west-1"
  kms_key_id = "alias/vault-auto-unseal-key"
  # При запуске Vault автоматически запрашивает расшифровку master key
}
```

## **Преимущества KMS**

### **1. Безопасность:**
- **Сертифицированные HSM** (FIPS 140-2 Level 3, Common Criteria)
- **Автоматическая ротация ключей**
- **Централизованное управление** политиками
- **Подробный аудит** всех операций

### **2. Соответствие требованиям:**
- **GDPR** - право на забвение, шифрование данных
- **HIPAA** - защита медицинских данных
- **PCI DSS** - защита платежных данных
- **SOX** - контроль финансовой отчетности
- **ФЗ-152** (Россия) - защита персональных данных

### **3. Операционная эффективность:**
- **NoOps / LowOps** - управляется провайдером
- **Автомасштабирование** под нагрузку
- **Интеграция** с другими облачными сервисами
- **Единый интерфейс** управления

## **Сравнение KMS vs HSM vs Vault**

| Критерий | Облачный KMS | Локальный HSM | Hashicorp Vault |
|----------|--------------|---------------|-----------------|
| **Управление** | Полностью managed | Самостоятельное | Самостоятельное |
| **Стоимость** | Оплата за использование | Высокие CAPEX | Средние OPEX |
| **Масштабирование** | Автоматическое | Ручное (докупать HSM) | Горизонтальное |
| **Интеграция** | Нативная с облаком | Требует интеграции | Универсальная |
| **Безопасность** | Доверие провайдеру | Полный контроль | Гибкий контроль |

## **Лучшие практики использования KMS**

### **1. Разделение ключей по назначению:**
```yaml
keys:
  - database-encryption: для шифрования БД
  - application-secrets: для шифрования секретов
  - ssl-tls: для TLS сертификатов
  - signing: для цифровых подписей
```

### **2. Иерархия ключей:**
```
Организация (Root Key)
├── Проект (Project Key)
│   ├── Сервис A (Service Key)
│   └── Сервис B (Service Key)
└── Другой проект...
```

### **3. Политики доступа:**
```json
{
  "Effect": "Allow",
  "Action": [
    "kms:Encrypt",
    "kms:Decrypt"
  ],
  "Resource": "arn:aws:kms:region:account:key/key-id",
  "Condition": {
    "StringEquals": {
      "kms:EncryptionContext:Service": "payment-service"
    }
  }
}
```

### **4. Мониторинг и аудит:**
- **Активировать CloudTrail / Audit Logs**
- **Мониторить аномальные активности**
- **Регулярные review политик доступа**
- **Тестирование DR процедур**

## **Критические риски**

### **1. Vendor Lock-in:**
- **Привязка к облачному провайдеру**
- **Сложность миграции** ключей
- **Зависимость от API** провайдера

### **2. Ключевые компромиссы:**
- **Доверие третьей стороне** (облачному провайдеру)
- **Юрисдикционные риски** (законы страны провайдера)
- **Доступ правительства** (через legal request)

### **3. Технические риски:**
- **Ошибки конфигурации** IAM политик
- **Человеческий фактор** (excessive permissions)
- **Сетевые задержки** при каждом шифровании

### **1. Multi-Cloud KMS:**

## **Вывод**

**KMS** — это критически важный компонент современной security-архитектуры, который:
- **Централизует** управление криптографией
- **Упрощает соответствие** регуляторным требованиям
- **Снижает операционную нагрузку** на команды
- **Повышает общий уровень** безопасности системы

**Для custody-service** (как в вашем случае) KMS является оптимальным выбором для:
- Auto-unseal Vault
- Хранения ключей шифрования данных
- Управления ключами подписей транзакций
- Соответствия финансовым регуляторам

KMS превращает криптографию из сложной экспертной задачи в управляемый сервис, доступный для любой команды разработки.
